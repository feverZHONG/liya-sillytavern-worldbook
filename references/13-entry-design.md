# 世界书条目设计规范

> **本文件管「条目怎么设计」**：靠什么进 / 放哪 / 要不要恒在场 / 怎么拆、怎么减 / 关系层放哪。
> **机制是什么**（判定链、字段、默认值、行号）→ `12-worldbook-mechanics.md`，本文只引用不重述。
>
> 反面教训（为什么需要这份文档）：曾把「泛词误触发」当成「删键」问题处理——只动了触发层的一个点，
> 忽略了扫描源（`scanDepth` / `match_*`）、来源分组（`character_strategy`）、注入通道（`position`）三层。

---

## 一、机制速览：五层可控点（详解见 `12-worldbook-mechanics.md` §0）

```
① 来源      四来源（独立书/卡内书/聊天书/人设书）× character_strategy（默认 character_first）
② 扫描源    最近 scanDepth 条聊天（每条带「名字: 」前缀）+ 按 match_* 拼进来的 6 类卡字段
③ 触发      装饰器 / constant / 主键 / 二级键 / 概率 / 包含组 / triggers
④ 排序预算  来源组内 order 降序 → 预算截断
⑤ 注入      position 七桶 + depth/role + outlet 宏
```

| 层 | 设计时能动的手（速查） |
|:--|:--|
| ① 来源 | `world_info_character_strategy`：卡内书（随卡、`character_first` 下组内优先）／独立书（共享、可 `characterFilter` 分流）——见 §五 |
| ② 扫描源 | 条目级 `extensions.scan_depth`（0＝不扫聊天）＋ 6 个 `match_*` 开关 |
| ③ 触发 | `constant` ／ 主键 ／ `secondary_keys`+`selective` ／ `@@activate` ／ `triggers` |
| ④ 预算 | `order`（同组内比较；跨来源由分组策略决定） |
| ⑤ 注入 | `extensions.position`（7 桶）＋ `depth`/`role`（at_depth 用）＋ `outlet_name` |

## 二、动笔三层选法（按顺序问自己）

### 第 1 层：这条靠什么进？（触发源）

| 这条信息的性质 | 用什么进 | 说明 |
|:--|:--|:--|
| 恒定事实，每轮都该在场 | `constant: true` | 吃预算，每卡 1-2 条为限 |
| 恒定事实，但只跟「挂这张卡」有关 | `scanDepth: 0` + `match_character_description` / `match_character_personality` 等 | 不占聊天词，卡在就在 |
| 话题相关（提到某人/某物才该讲） | 主键 = **关系方的专有名称** | ⚠️ 本体角色名无意义（每轮都在扫描区） |
| 话题相关，但要更严（A 且 B） | `selective: true` + `secondary_keys` | 默认 AND_ANY；别在想要「任一词触发」时误开 |
| 踩雷才炸（禁忌/底线） | **短语键**（`includes` 匹配整串） | 例：「替我做决定」而不是「决定」 |
| 只在该类生成里出现 | `extensions.triggers` | normal/continue/impersonate/swipe/regenerate/quiet |
| 由别的条目带出来 | 递归（全局默认关）＋ `exclude_recursion` / `prevent_recursion` / `delay_until_recursion` | 见机制文档 §6 |

### 第 2 层：进来后放哪？（注入通道）

| 内容性质 | position | 理由 |
|:--|:--|:--|
| 角色关系、身份、性格锚点 | `after_char`（默认） | 紧贴角色定义，属「她是谁」 |
| 世界/机构/地点/术语 | `before_char`（或进独立共用书） | 属背景层，先于角色出现 |
| 禁忌、当下情绪、需要强影响的近处设定 | `at_depth`（配 `extensions.depth`、`role`） | 贴近当前对话，模型注意力最强 |
| 需要精确落点的设定 | `outlet` + `{{outlet::名称}}` 宏 | 可插进 prompt 任意位置（由宏决定） |
| 与作者注记同层 | `AN_top` / `AN_bottom` | 作者注记前后 |
| 与示例消息同层 | `EM_top` / `EM_bottom` | 示例区前后 |

⚠️ 卡侧顶层 `position` 只认 `before_char`/`after_char`；其余六桶必须写 **`extensions.position`（数值）**——
`convertCharacterBook` 优先读 `extensions.position`（:5636）。

### 第 3 层：要不要恒在场？（预算）

- 预算 = `world_info_budget`（默认 25%）× 上下文，再被 `budget_cap` 截断。
- **来源分组先于 order**：默认 `character_first` 下卡内书整体先被考虑，共用书在后 —— 跨书优先级不用靠 order 段位去争。
- 常量 > 直接命中 > 递归命中；同级按 order 大者优先。
- 尺度参考：一个 16 角色项目实测——共用书 13 条／约 1600 token／0 常驻；单张卡内书 5-9 条／500-1700 token。
  单卡单轮通常命中 1-3 条。**常驻条一旦超过 2 条，预算就紧张**。

## 三、硬判据（从机制推出来的，写条目时逐条对）

1. **本体角色名不进键**——扫描区每轮都带「名字: 」前缀，用本体名当键＝隐性常驻，没有触发意义。
2. **泛词不进主键**——`决定/过去/经历/责任/结构/实验/游戏/研究员/老师` 这类，无关对话里必现；
   要话题触发就改短语键或收紧 `scanDepth`。
3. **「世界内唯一指代」可作键**，但要有档案出处——例如某角色被某角色专称的绰号、专用代称
   （这类词在该世界里只指向一个人，等于专有名词）。
4. **恒定事实别靠键猜**——用 `constant` 或 `match_*`；靠键猜「这轮是不是在聊这个」只会两头顶：
   聊到了漏、没聊到还中。
5. **位置按语义选**，别一律 `after_char`；要贴近对话就用 `at_depth`。
6. **一条只干一件事**——把「关系 + 背景 + 禁忌 + 口头禅」塞一条会让触发条件没法设计（要么全进要么全不进）。

## 四、判据的来处（实测记录）

- **泛词误触发 4/4**（`bin/wb sim`）：无关语境下「决定」「过去」「老师」「结构」各带进一条无关条目。
- **本体角色名当键＝隐性常驻**：扫描文本每条带「名字: 」前缀——用本体名当键没有触发意义。
- **`character_first` 是默认**：卡内书整体先于独立书进预算，「卡内关系压过共用书」不靠 order 段位保证。
- 工具：体检 `bin/wb check --all`；触发验证 `bin/wb sim <卡> "句子" --book <书>`（把「我以为会触发」变成「实际会不会」）。

## 五、关系层架构：两套方案并列（2026-09-25 阁下定「都登记」，判据按卡的分发形态）

> **先问一句再选**：这张卡会不会**单独分发 / 单独使用**？
> - 会（单张卡面，用户只拿走这一张）→ **方案 A · 卡内书**
> - 不会（成套使用、多卡共享同一批角色关系事实）→ **方案 B · 独立关系书**
>
> 两者不是新旧替代关系，**各有各的位子**；同一个项目里也可以并存（见 6.4）。

### 5.1 判据表

| 问题 | 是 → | 否 → |
|:--|:--|:--|
| 这张卡会单独发给别人（自带一切）？ | **A** | 继续问 ↓ |
| 同一批关系事实要被多张卡共用、要一处维护？ | **B** | **A** |
| 关系条目只有这一张卡用、量小（≤10 条）？ | **A** | 考虑 **B** |
| 卡名可能改、且不想承担断链风险？ | **A** | **B** 可接受（卡名当主键） |

### 5.2 方案 A · 卡内书（`data.character_book`）

**适用**：单张卡面分发；角色专属关系；条目量小。

**规格**
- 位置：`data.character_book.entries[]`（V2 spec）；顶层 `character_book` 不参与读写
- 条目字段用**卡侧写法**：`keys`（数组）、`secondary_keys`、`insertion_order`（数值）、`position`（字符串 `before_char`/`after_char`）、`enabled`、`constant`、`content`、`extensions.*`
- 细位置（AN/EM/@D/outlet）必须写 `extensions.position`（数值）——顶层 `position` 只认 before/after
- 随卡导出自动嵌入；分享一张卡即完整

**实施要点**
1. 关系条目建议 `position: after_char` + `order: 300-390`（紧跟角色定义）
2. 键只用**关系方专有名称**（本体角色名无触发意义，见 §三·硬判据 1）
3. 分组上属 `characterLore` → 默认 `character_first` 下**优先于独立书**
4. 恒在场的关系用 `constant`（每卡 1-2 条为限）

**限制**
- ❌ 无法按角色/标签过滤（`convertCharacterBook` 转换时丢掉 `characterFilter`）
- 改一处要动卡（但只有这一张卡，不构成成本）
- 世界层内容不要塞这里（那是共用书的职责）

### 5.3 方案 B · 独立关系书（`.json` + `characterFilter`）

**适用**：成套使用、多卡共享同一批角色关系事实、要一处维护。

**规格**
- 形态：独立 `.json`（**ASCII 文件名**，文件名＝关联键）
- ⚠️ **一张卡只能自动带一本书**（`data.extensions.world` 是单值，ST 的卡↔书关联是一个下拉）→ 分层要「**清单分层、部署合并**」：世界层与关系层各自一份清单文件，生成时 `wb new 世界清单.json 关系清单.json --out 共用书.json` 合并成一本，卡上的 `extensions.world` 一个字都不用改。想分两本＝用户每张卡都得在酒馆里手动开第二本，容易漏
- 条目字段用**WI 侧写法**：`key`（数组）、`order`（数值）、`position`（数值）、`characterFilter{ isExclude, names, tags }`、`extensions.*`
- 卡侧关联：`data.extensions.world = "<文件名不含 .json>"`
- 分发：**书要跟卡一起给**（缺书＝关系层消失）

**实施要点**
1. 每条用 `characterFilter.names = ["<卡文件/avatar 文件名>"]` 分流；`isExclude: false`（默认）＝只对名单内角色生效
2. 也可按**标签**分流（`tags` + `isExclude`）
3. 组上属 `globalLore` → 与共用世界书同组，靠 `order` 段位排序：**世界 110-178 ＜ 关系 250-289 ＜ 卡内 300-390**（段位分开，同一 position 桶落在一起时卡内在前）
4. 同一条只写给「需要它的卡」——一本 100 条也只有匹配当前卡的几条进求值（被 filter 掉的 `continue`），**书大不等于每轮贵**

**限制 / 脆点**
- ⚠️ `characterFilter.names` 用的是 **avatar 文件名去扩展名**——**卡改名即断链**（与 `extensions.world` 同族脆弱约定），改名要全线同步
- 单卡场景里它是纯负担：多带一个文件 + 卡名耦合，没有收益

### 5.4 三层并存的推荐组合（成套项目）

```
共用世界书（世界层：机构/地点/术语，0 常驻，13 条级）        ← 谁都能用
关系书（关系层：跨卡共享的角色关系事实，characterFilter 分流）
卡内书（卡专属：只这一张卡需要的关系/禁忌/口癖）
卡 description / depth_prompt（卡自己的 PList，不进世界书机制）
```

**分工原则**：世界进共用书、跨卡共享的关系进关系书、只这一张卡要的进卡内书、卡自己的性格口癖留在 PList。

实测（一个 16 角色项目，2026-09-25）：世界层 13 条 1598 token ＋ 关系层 30 条 2208 token → **合并成一本**（43 条 3806 token，0 常驻）；单卡实测命中 **0-212 token**（说不相关的话就是 0），卡内书另 1-2 条 50-163 token。

### 5.5 A ↔ B 互转注意

| 项 | A（卡内书） | B（独立书） |
|:--|:--|:--|
| 键字段 | `keys` | `key` |
| 顺序字段 | `insertion_order` | `order` |
| 位置字段 | 字符串 `position`（+`extensions.position` 数值） | 数值 `position` |
| 过滤器 | **无此字段** | `characterFilter` |
| 关联 | 嵌在卡里 | `extensions.world` 指文件名 |

迁移后必须验证：`wb ls <文件>`（自动识别两种形状）→ `wb check --all`（二级键门槛/通用词/撞车/预算）→ `wb sim <卡> "句子" --book <书>`（双书同跑，看位置桶分列）。

## 六、拆分与做减法（2026-09-25 阁下定，动手前必守）

> 原话要点：**做好拆分、做减法**。条目不是越多越全，是越准越省。

### 6.1 拆：一条只干一件事

一条里塞了「关系 ＋ 表现 ＋ 禁忌 ＋ 台词」→ 触发条件就没法设计（要么全进、要么全不进）。
拆到「能独立回答一个问题」为止：**这两人是什么关系？** / **他的禁忌是什么？** / **这件装备是什么？**

### 6.2 减：四道闸（按顺序问，任何一道答「是」就挪走或删）

| 闸 | 问 | 处理 |
|:--|:--|:--|
| ① | **卡本体已经写了吗？**（`description` / `depth_prompt` 的 PList / `system_prompt` / `post_history_instructions`） | **删**——卡本体是每轮都在的，世界书再写一遍＝双倍占位 |
| ② | **属世界层吗？**（机构 / 地点 / 装备 / 术语） | **挪共用世界书** |
| ③ | **是恒定性格或口癖吗？** | **挪 PList**（每轮都该在，但不该由世界书机制去猜） |
| ④ | **只有提到才需要？** | ✅ 这才是世界书的位子 |

**推论**：世界书条目的**唯一存在理由**是「按需展开」——即「PList 里那一行标签的展开」。
PList 写「被某人叫某个专属绰号」，世界书条目的价值就在于补「这个人是谁、为什么这么叫、被叫时的反应」，
**不是**把标签原句再念一遍。

### 6.3 删哪几类（现有条目的通病）

- 「角色会这么说：…」台词样例 → 删（台词归 `description` 的 Ali:Chat / `mes_example`）
- 「表现：会炸毛 / 会无奈 / 会委屈」→ 删（AI 从关系与性格能推断，写了等于替它演戏）
- 临时状态细节（最近在练什么曲子、在忙什么）→ 删（不是设定，会过期）
- 与 PList 重复的标签句 → 删
- 社群玩梗外号（非设定）→ 删

### 6.4 目标尺度

- 单条 **60-90 字**；一条一义
- 关系条目数量按「**有关系且需要展开的人物数**」走，不按「能写多少」走
- 每卡常驻 ≤ 2 条；卡内书条目总数 ≤ 6 条
